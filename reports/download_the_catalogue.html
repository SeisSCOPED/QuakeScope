Downloading the QuakeScope pick catalogue for a region and a period¶

The first notebook reads one network-month. This one does what a study needs: choose stations by place and time, mirror every partition that covers them, query the mirror, check which station-days were actually processed, and export for an associator. Anonymous throughout; nothing here needs an AWS account. Coverage comes from the public availability table (one row per station-day), and duplicate rows are dropped on read.

Worked example: the Monte Cristo Range, Nevada, M6.5 of 2020-05-15, with a 1.5 degree box and the two months from May 1 to June 30. Change the four values in section 2 and everything below follows.
bucket s3://quakescope-picks-2026, us-east-2, public-read
catalogue western: 1986 to September 2026, PhaseNet original, P and S thresholds 0.2 (three campaign eras, the fill stations, the October re-read and repairs, all under one prefix). Set CATALOGUE to obs or quakescope-2025 and the same cells work
layout <campaign>/picks/network=<NET>/year=<YYYY>/month=<MM>/<shard_id>.parquet, plus manifests/, runs/, stations.parquet
reference docs/data_access.md

Runtime: about ten minutes on a laptop, most of it the download; re-runs skip files already mirrored.

Stations in the box, operating in the period¶

stations.parquet is the table the catalogue was planned from. start_date and end_date are Parquet dates, so they compare directly with a datetime.date; a station still operating carries 3000-01-01 rather than a null, so a filter like end_date >= START keeps it instead of dropping it.

Until 2026-09-29 these two columns were a YYYY.DDD float, which is kept beside them as start_yearday and end_yearday. Do not decode that float by formatting it as a string: str(2010.21) is "2010.21" and reads as day 21, where the value means day 210.

3. Which partitions cover them¶

A partition is (campaign, network, year, month). The era decides the campaign; a network partition holds every station of that network, so the station filter is applied to the rows after the download (section 5).

In [5]:
def partitions(networks, start, end):
    out = []
    d = start.replace(day=1)
    while d <= end:
        for net in networks:
            out.append((CATALOGUE, net, d.year, d.month))
        d = (d.replace(day=28) + datetime.timedelta(days=4)).replace(day=1)
    return out

PARTS = partitions(NETWORKS, START, END)
print(f"{len(PARTS)} partitions, e.g. {PARTS[:3]}")

4. Mirror them¶

One listing per partition, then every missing file in parallel. s3fs fetches concurrently and lands at 15 to 20 MB/s from a laptop; the AWS CLI is the same speed (aws s3 sync --no-sign-request <s3 prefix> <local dir>, one line per partition, printed below for people who prefer a shell).

In [6]:
def sync(camp, net, year, month):
    # Mirror one partition; return (files fetched, bytes fetched, files already present).
    prefix = f"{camp}/picks/network={net}/year={year}/month={month:02d}/"
    local = MIRROR / prefix
    local.mkdir(parents=True, exist_ok=True)
    try:
        remote = fs.ls(f"{BUCKET}/{prefix}", detail=True)      # one LIST
    except FileNotFoundError:                                  # no picks were written for this partition
        remote = []
    have = {p.name for p in local.glob("*.parquet")}
    todo = [o for o in remote if Path(o["name"]).name not in have]
    if todo:
        fs.get([o["name"] for o in todo], [str(local / Path(o["name"]).name) for o in todo])
    return len(todo), sum(o["size"] for o in todo), len(have)

t0 = time.time(); n_new = b_new = n_have = 0
for camp, net, year, month in PARTS:
    n, b, h = sync(camp, net, year, month)
    n_new += n; b_new += b; n_have += h
print(f"fetched {n_new:,} files, {b_new / 1e6:,.0f} MB in {time.time() - t0:.0f} s; {n_have:,} already mirrored")
empty = [p for p in PARTS if not any((MIRROR / f"{p[0]}/picks/network={p[1]}/year={p[2]}/month={p[3]:02d}").glob("*.parquet"))]
print(f"{len(empty)} of {len(PARTS)} partitions hold no picks at all: {sorted({p[1] for p in empty})}")

5. Query the mirror¶

DuckDB over the local tree, with the partition keys read from the paths. DISTINCT ON (tid, cha, pha, peak) drops the duplicate rows that interrupted Spot attempts left in the bucket (about 64 M of 2.13 B western rows on 2026-10-13; the picker is deterministic, so a repeated key is the same pick). The station filter is a join against the selection table, so nothing outside the box is counted. Everything comes back aggregated; the raw rows are only pulled where they are needed.

The threshold is yours to choose¶

Everything at or above 0.2 is stored. How much a higher floor removes depends on the station and the sequence, so look before choosing.

6. Coverage: which station-days were read¶

A station-day with no rows may mean the archive held nothing, that the data held no arrival above 0.2, or that the campaign never read it. The availability table separates them: one row per station-day inside each station's FDSN operating epochs, built from every job manifest, public, one file per network at <catalogue>/availability/network=<NET>/availability.parquet.

status meaning
loaded read and picked; npks picks that day, 0 means data and no arrival above 0.2
no_data the archive listing held nothing that day
not_found the archive has no such network-year
empty_read an object exists but holds no pickable band (detail names what it holds)
unread attempted, not read (detail: too_big, read_error, ...)
unknown inside the station's epochs, no record either way

The table covers days inside a station's FDSN channel epochs, which can be narrower than the start_date to end_date window of stations.parquet. Days in the window but outside every epoch have no row; the cells below call them outside FDSN epochs.

unknown is mostly shards from before image d0ccf9b (2026-10-06), which recorded only what they read; the strong-motion network NP, which had no data in a 1,408-day sample and was not re-read; and the networks our account may not read (TD, EO, LH). The 2025 catalogue's table is not built yet; its manifests carry records only, so a 2025 station-day is either read or unknown.

def availability(catalogue, net):
    try:
        return pd.read_parquet(f"s3://{BUCKET}/{catalogue}/availability/network={net}/availability.parquet",
                               storage_options={"anon": True})
    except FileNotFoundError:
        return pd.DataFrame(columns=["tid", "date", "status", "cha", "npks", "detail"])

t0 = time.time()
av = pd.concat([availability(CATALOGUE, n) for n in NETWORKS], ignore_index=True)

For an associator¶

PyOcto takes a DataFrame with station, time, phase and probability; GaMMA takes id, timestamp, type, prob and amp. Both want the station table alongside. The mapping is the whole conversion; a confidence floor of 0.5 is a reasonable starting point for association and is not the catalogue's floor.

8. Scaling up¶

The recipe above is the recipe at any size; only the byte counts change.

A whole network-year. Replace the month loop with the year:

aws s3 sync --no-sign-request s3://quakescope-picks-2026/western/picks/network=UW/year=2019/ quakescope_mirror/western/picks/network=UW/year=2019/

The whole western catalogue, 55.3 GB in 580,407 objects (Parquet footers and S3 listing, 2026-10-13), about two hours on a fast link:

aws s3 sync --no-sign-request s3://quakescope-picks-2026/western/picks/ quakescope_mirror/western/picks/
aws s3 cp   --no-sign-request s3://quakescope-picks-2026/western/stations.parquet quakescope_mirror/western/
aws s3 sync --no-sign-request s3://quakescope-picks-2026/western/availability/ quakescope_mirror/western/availability/

The availability tables for all of western are about 0.1 GB.

The 2025 catalogue for the same stations is under quakescope-2025/picks/ with the same partitioning (88.3 GB in 42,570 objects for all 453 networks, S3 listing of 2026-10-19); its stations.parquet keeps the YYYY.DDD date strings of the database.

Keeping a mirror current. Duplicate removal and compaction will rename objects without changing picks; aws s3 sync re-run against the same local tree fetches only what changed. Record the date of any pull you publish from.
