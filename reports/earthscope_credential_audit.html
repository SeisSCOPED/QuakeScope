EarthScope Credential Audit

Five defects in one file turned every EarthScope refusal into thousands of repeat requests. Every claim below links to the line that caused it and the line that replaced it, and ships with a test you can run on your own account without touching ours.

What happened

Your report was that our workers were effectively denial-of-servicing the credentials endpoint, that 400/403/404 answers were being retried aggressively, and that some requests asked for a temporary network without a year — a request that can never succeed. All three are correct. We found the mechanism behind each and have the logs for all of them.

Everything is in one file, sb_catalog/src/s3_helper.py, in the build that was running: c5846f3. The multiplier that turned single refusals into request storms is that CompositeS3ObjectHelper.get_filesystem() is called once per day per network by the listing loop and once per object by the read path. For one network in one year-long, 30-station shard that is 11,315 calls. Nothing remembered a refusal, so nearly every one of those calls became a request.

The account block then made it worse rather than better. A rejected refresh token surfaces from earthscope_sdk as InvalidRefreshTokenError, which carries no .response attribute — so it fell straight past our HTTP status handling into a generic retry loop that re-ran the refresh grant five times per scope. Once the token was rejected, every network took that path at once, on 208 workers.

From our own CloudWatch logs, log group /aws/batch/job in us-east-2. Each line counted is one POST https://login.earthscope.org/oauth/token issued by a worker, and in this window every one of them came back invalid_grant · user is blocked.

The five defects

Every heading below links to the exact lines on GitHub — red to c5846f3, the build that was running, green to 713698e on PR #32.

D1

A refusal was never remembered

Successful credentials were cached by scope. Refusals were not — so every one of the 11,315 calls per shard re-ran the exchange and re-asked a question you had already answered.

The store lives at module scope, not on the helper, because a worker claims shard after shard in one process and built a fresh helper each time — per-instance memory was discarded every few minutes. It keeps the exception's class and message rather than the caught instance, so a long-lived worker does not pin every frame the exception passed through.

s3_helper.py#L172-L178process-wide store
_ES_STATE = {
    "refused": {},        # scope key -> terminal verdict, never re-asked
    "auth_failed": None,  # 401: not scoped to a network, so it stops everything
    "exchanges": {},      # scope key -> [monotonic stamps], for the rate limit
    "denials": {},        # scope key -> consecutive AccessDenied count
    "client": None,       # the one earthscope_sdk client this process uses
}

Related: es_verdict and es_record_verdict, and the terminal-type list ES_TERMINAL. Every 4xx has a type in that tuple — including EarthScopeRequestRefused for statuses we have not seen yet, so none can slip past the store and be re-asked.

D2

Escalation removed scope instead of adding it

The source of the year-less temporary-network requests. On any denial the client flipped a network's scoping to "the other one" — and for a temporary code, the other one drops the year.

Two things made this severe. It was reachable from a 403, because EarthScopeNotEntitled subclassed RuntimeError and the handler in D1 caught it — the one status where a differently-shaped request is guaranteed useless. And the read path called it once per object.

Escalation now only ever adds the year, only fires on a 400, and runs at most once per network. A request that cannot succeed is answered locally instead of being sent:

        f"and EarthScope authorises them per year. A year-less request "
        f"can only ever return 400, so it is not sent."

D3

A new SDK client on every call

Your note that the workflow did not appear to be reusing credentials was literally true at the library level: we built a fresh EarthScopeClient inside the exchange function.

s3_helper.py#L502-L510c5846f3
for attempt in range(1, ES_CREDENTIAL_ATTEMPTS + 1):
    try:
        with EarthScopeClient() as client:
            return client.user.get_aws_credentials(
                role=EARTHSCOPE_ROLE, ...)
s3_helper.py#L781-L785713698e
for attempt in range(1, ES_CREDENTIAL_ATTEMPTS + 1):
    try:
        return self.es_client().user.get_aws_credentials(
            role=EARTHSCOPE_ROLE,
            ttl_threshold=self.ttl_threshold,
            **scope,)

In earthscope-sdk 1.8.0, _UserService caches issued credentials in _aws_creds_by_key, an instance attribute, and nowhere else — the on-disk credential cache 1.3.x had was removed. A client per call therefore discarded that cache every time and guaranteed a round trip, plus an OAuth refresh whenever the access token had not been persisted. es_client() now returns one client for the life of the process.

D4

Auth failures fell into the generic retry loop

The defect that produced the traffic in the chart above. We special-cased 401 and 403 and read exc.response.status_code for everything else — but an AuthFlowError has no .response, so it reached the retry loop and slept.

    # Every remaining AuthFlowError is about OUR credentials, not about
    # this scope: InvalidRefreshTokenError, NoRefreshTokenError, the
    # device-code errors. None is congestion, and none is fixed by asking
    # again - but they carry no `.response`, so the status-code branch

EarthScopeAuthFailed is recorded in _ES_STATE["auth_failed"] rather than per scope, and es_verdict() checks it first — a rejected token is not a fact about a network, so one rejection stops every network in the process at once. The retry loop that remains handles only 429 and 5xx, with exponential backoff, full jitter and Retry-After. The old fixed 5-second sleep put every worker that saw the same blip back on your endpoint at the same instant.

D5

A shadowed handler spun a tight loop on the access point

Present since June and invisible until we went looking. PermissionError and FileNotFoundError both subclass OSError, and an OSError handler sat before both — so neither could ever run.

s3_helper.py#L936-L945c5846f3
except OSError as e:
    if e.errno == 5:
        return obspy.Stream()
    # AccessDenied has errno None -> falls through,
    # returns nothing, `while True` goes round again
except PermissionError as e:        # unreachable
    ...
except (FileNotFoundError, ...):   # unreachable
s3_helper.py#L1364-L1418713698e
except PermissionError as e:
    denied += 1
    scope_denied = self.s3helper.note_access_denied(net, year)
    ...
except FileNotFoundError:
    return obspy.Stream()
except OSError as e:
    if e.errno == 5: ...

s3fs maps AccessDenied to PermissionError constructed with a message and no errno. So a denied object fell out of the OSError branch without returning, the while True loop went round, and the object was re-HEADed as fast as the socket allowed until the 900-second station-day timeout.

The logs confirm the shadowing rather than infer it. Across the full five-day CloudWatch retention, the two log lines that only the PermissionError branch can emit never appear once:

filter_log_events · /aws/batch/job · full 5-day retentiondead code, confirmed
       0  "Credential refreshed after access denied"   ← PermissionError branch
       0  "Access denied ... times for"                 ← same branch, budget spent
       0  "Not authorized to access this resource"      ← OSError errno==5 branch
      18  "Timeout after"                               ← the 900 s station-day cap

Not one line from the branch in five days of production. It also means the ES_DENIED_ATTEMPTS budget that was supposed to bound credential refreshes had never once executed. In fairness to the record: during the blocked window workers were failing earlier, at the credential stage, so this defect was not a major contributor to the traffic in the chart — but it is real, it was live, and the 18 station-day timeouts are its observable symptom.

The fixed order is pinned by a test that parses the handler chain and asserts each narrow type precedes OSError, so it cannot regress silently.

Smaller changes in the same pass

  • Per-scope denial accounting. The refresh budget lived in a local that reset on every object. note_access_denied counts per scope and resets only when a read on that scope succeeds.
  • A local rate limit. _es_throttle refuses more than three exchanges of the same scope in five minutes, raising without sending anything. A credential is valid for an hour.
  • Paced diagnostics. netyear_sweep probes every planned network-year — about 1,600 — and now takes a --pace (default 0.25 s) instead of firing as fast as the socket allows.
  • Quieter logs. A cached verdict is logged once per network rather than once per day, so log volume no longer tracks the bug.

Which credentials are which

Worth being explicit about, because it determines what you need in order to test this: nothing in our AWS account grants access to your archive. s3-miniseed-v2 is an EarthScope role alias, not an IAM role in our account, and the credentials that read data are issued by you.

For your records — the whole of the AWS-side configuration, none of which is needed to run the test. This page is public, so account and secret identifiers are described rather than printed; ask and we will send the full ARNs directly.

What we are asking

Not to be unblocked first. Run the checks, tell us whether the traffic shape is one you are willing to accept, and we will hold the fleet at zero until you say so.

Three things would help us not get here again:

  • Confirmation that the scoping rule is what we think it is. We treat FDSN codes starting with a digit or X/Y/Z as requiring a year, and everything else as network-only. That is a guess from your documentation, not something we measured, and a wrong guess in either direction costs a request. If you have an authoritative list, we will use it instead.
  • Whether a 403 on network+year can ever become a 200 with a different scope. We now assume no, and never retry. If that is wrong for some case, we would rather know than guess.
  • A rate you are comfortable with. The client has a local limiter (ES_REFRESH_BUDGET, ES_REFRESH_WINDOW) and both are environment variables. Name a number and we will set it. Our planning sweep now paces at 0.25 s between probes; say the word if that is still too fast for ~1,600 network-years.

Caching on your side is worth doing regardless, but it should not have been what protected you from this. The client was wrong and it is our fix to make.
