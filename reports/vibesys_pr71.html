VibeSys optimizations: pick precision and computational cost

PR #71 proposes CPU optimizations for the QuakeScope picker, found by an automated optimization campaign and reported at 8.5× on an Intel AMX host. This page tests whether the picks survive and what the speed is on the hardware we would use: the leaderboard's own waveforms and analyst picks for precision, and an M1 Max laptop and three AWS Graviton generations for cost.

Verdict

The fp32 path keeps the catalogue and runs six times faster on Graviton; bf16 changes the catalogue

Accept: fp32 forward pass, fast annotate, amplitude rewrite

With the PR's settings in fp32, 26,529 of 26,531 picks at threshold 0.2 are identical to vanilla to the millisecond; the other 2 are one sample apart on flat-topped peaks. Wood-Anderson and velocity amplitudes agree to 9e-12 relative. On the same Graviton instance the PR reproduces 10,619 of 10,620 vanilla picks, fewer differences than vanilla itself shows between Graviton2 and Graviton3 (4). Compute time falls 5.9× to 6.6× on Graviton, and 1.17× on an M1 Max laptop.

Do not accept: bf16 chosen per host

bf16 inference leaves 87 % to 90 % of picks identical, moves 10 % to 13 % by at least one sample and makes 1.6 % appear or disappear. Recall against analyst picks does not change, but the PR enables bf16 automatically on CPUs with AMX-BF16, so a catalogue built on mixed Spot capacity would carry two numerical paths with no record of which ran where. Precision should be an explicit campaign setting, default fp32, written into the run records.

Proposed rule

Every pick within ±1 sample (10 ms at 100 Hz), which is under half the tightest analyst figure above, and no pick lost or gained unless its confidence is within 0.05 of the threshold.

Where the time goes

Most of the gain is the Wood-Anderson rewrite: vanilla spends 395 s of worker time on it on Graviton2 against 23 s for the PR. Picking gains 1.9× on Graviton2 and 1.7× on Graviton4, and is slightly slower on Graviton3. The C velocity kernel does not build on ARM, so its SciPy fallback ran.

Why the laptop gains less

No macOS arm64 torch build has oneDNN (checked: conda-forge 2.13.0 and the official pip wheel 2.14.1, both USE_MKLDNN=OFF), so the PR's fused kernels cannot run on an Apple M-series CPU, and its picking runs 1.34× slower there through an equivalent plain-torch path. The laptop's net 1.17× is the amplitude code alone. aarch64 Linux torch 2.14.1 has oneDNN, which is why Graviton gains six times.

Limits and other findings

What this does not show

Not covered

  • jma_wc, the global weight and the one the PR's own evaluation used, was not scored here.
  • obs (PickBlue) cannot use the optimized path: fast annotate raises does not cover this model setup: ['padding/filter'] when the model is built.
  • bf16 was emulated on the laptop, not run on AMX hardware.
  • Fargate was not timed; S3 reads and Parquet writes are outside every timing above.
  • Streams the model resamples (30 of the 130 precision windows) fall back to SeisBench's annotate; the timing workload is 100 Hz only.
  • The 707-line s3_helper.py rewrite (overlapped reads, per-station listing) was not reviewed.

Defects found

  • PhaseNetGraph with fused=False and polyphase deconvolution crashes on torch builds without oneDNN (fast_forward.py:220, a view of a tensor that is not channels-last).
  • veliir.c calls __builtin_cpu_init, which is x86-only; on ARM the build fails and SciPy runs. Built for arm64 with the probe guarded, it matched SciPy to 10-11.
  • seisbench==0.12.5 has no aarch64 wheel: an ARM image needs python3-devel and gcc. Four workers importing SeisBench for the first time at once can race on its cache config.
  • As merged, nothing selects the optimized settings, so production would run vanilla.

Reproduce

Code and data

Harness in scripts/vibesys_pr71/: run_arm.py (the three arms, with the AMX emulation in emu.py), score.py and tolerance.py (scoring), run_amps.py (amplitudes), bench_worker.py with bench_run.sh (laptop timing) and ec2_run.sh (Graviton timing, run from EC2 user-data with presigned URLs; the instances terminated themselves). Shell scripts keep the paths of the 2026-10-26 run. export_results.py writes the tables in docs/benchmark/results/vibesys_pr71/, and this page is built from them by scripts/build_vibesys_report.py.
